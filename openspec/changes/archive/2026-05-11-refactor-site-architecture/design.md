## Context

当前项目是一个基于 Astro 的静态内容站，页面已经具备首页、归档、标签和文章详情等核心能力，但公共导航、侧边栏、主题控制、搜索入口、播放器和多种全局覆盖层仍然分散在页面与组件内部。现有实现的问题主要集中在四个方面：

- 全站壳层不完整，公共 UI 需要由页面重复装配。
- 页面布局与样式模式重复，首页、归档、关于页等共享相同的三栏结构却没有统一模板。
- 内容查询与聚合逻辑缺乏共享层，文章列表、分类树和标签数据在多个位置重复获取和排序。
- 客户端交互组件依赖全局 DOM、全局事件和隐式单例，难以复用，也容易在功能增多后出现运行期冲突。

本次设计面向一次渐进式重构，而不是推翻现有站点。目标是在不改变站点内容模型和整体视觉风格的前提下，先建立稳定的分层，再逐步迁移现有页面与组件。

## Goals / Non-Goals

**Goals:**

- 建立统一的站点壳层，集中管理顶部导航、全局搜索入口、主题控制、CRT 效果、移动端提示和页脚。
- 建立统一的页面布局模式，减少公共结构、响应式规则和窗口样式的重复定义。
- 建立共享的内容查询层，统一文章、分类和标签的数据来源与排序规则。
- 为客户端交互组件定义稳定的初始化与事件边界，减少对全局 DOM 的耦合。
- 支持根路径与子路径部署，统一页面链接和静态资源地址生成方式。

**Non-Goals:**

- 不更换 Astro、Markdown/MDX 或现有内容集合模型。
- 不在本次变更中重写主题系统的视觉设计。
- 不新增外部后端服务，也不引入复杂状态管理框架。
- 不以一次性重构替换所有页面，优先采用兼容现状的渐进迁移方式。

## Decisions

### 1. 引入分层布局体系

将当前 `BaseLayout` 拆解为更清晰的职责层次：

- `BaseDocument` 或等价基础布局负责 `html/head/body`、SEO、全局样式和首屏主题引导脚本。
- `SiteShell` 负责全站公共 UI，包括 `TopNav`、`SearchModal`、`ThemeSelector`、`CRTOverlay`、`MobileWarning` 和页脚。
- 面向内容页的布局组件负责具体页面结构，例如双栏/三栏主区域和文章页布局。

这样做的原因是当前公共能力存在于多个层级中，页面必须手工决定哪些公共组件需要出现，导致公共体验不一致。通过壳层收口后，页面只需要描述自己的主体内容。

备选方案是保持 `BaseLayout` 不动，仅通过约定要求页面自行引入更多公共组件。该方案实现快，但无法从结构上消除重复，也不能解决搜索与全局事件挂载不稳定的问题，因此不采用。

### 2. 提取统一的路径与资源构建模块

新增项目内部路由辅助模块，例如 `src/lib/routes.ts`，集中提供：

- 页面路径构建函数，如文章、标签、归档、首页链接。
- 静态资源路径构建函数，如 favicon、Pagefind 资源地址。
- 当前路径归一化逻辑，用于导航激活态判断。

这样做的原因是 `import.meta.env.BASE_URL` 目前散落在多个页面和组件中，且部分资源路径仍然写死为根路径。将路径规则集中后，可以同时支持根路径和项目子路径部署，避免逻辑漂移。

备选方案是在每个组件中继续局部处理 `BASE_URL`。该方案会维持现状问题，并在后续新增页面或资源时继续复制错误模式，因此不采用。

### 3. 提取共享的内容查询层

新增项目内部内容访问模块，例如 `src/lib/posts.ts`，负责：

- 获取已发布文章集合。
- 按统一规则排序文章。
- 构建分类树。
- 聚合标签集合与标签对应文章。

页面与组件不再直接承担内容聚合逻辑，而是消费共享函数返回的结构化数据。这样可以保证归档页、标签页、侧边导航和首页对文章可见性与排序顺序保持一致。

备选方案是让 `SideNav` 或各页面继续自行调用 `getCollection('posts')`。该方案短期简单，但会长期放大重复与行为不一致，不采用。

### 4. 客户端交互组件改为作用域初始化

搜索弹窗、播放器、视频嵌入和类似的交互组件改为基于组件根元素初始化，避免：

- 使用硬编码全局 `id`
- 使用 `document.querySelector()` 直接扫描整个页面
- 通过 `window` 暴露隐式 API
- 假定组件在任意页面中只会出现一次

推荐模式是每个组件只查询自己的根节点，并在必要时通过显式事件或数据属性与壳层通信。对全站共享行为，例如主题切换和全局搜索开关，应由壳层统一管理。

备选方案是继续保留全局事件和全局 DOM 选择器，只在发现冲突时局部修补。该方案风险高，且会让未来的组件复用成本持续上升，因此不采用。

### 5. 采用渐进迁移顺序而非一次性重写

迁移顺序按风险与收益排序：

1. 先修复全站壳层与搜索挂载问题。
2. 再统一路径与资源构建方式。
3. 然后抽离内容查询层。
4. 最后迁移播放器、视频框和其他客户端交互组件。

这样可以先解决运行期最脆弱的全局边界问题，同时避免在同一阶段同时重写页面结构和交互行为。

## Risks / Trade-offs

- [页面迁移期间新旧布局并存] → 通过兼容式布局组件逐页迁移，避免一次性替换所有页面。
- [抽离路径助手时可能引入链接回归] → 为首页、归档、标签和文章详情建立最小验证清单，确保根路径和子路径场景都可检查。
- [抽离内容查询层时可能改变现有排序或分类输出] → 先复刻当前行为，再在实现阶段显式比对首页、侧边栏和标签页结果。
- [交互组件改为作用域初始化后，壳层通信方式需要重建] → 将全站级行为保留在壳层，组件间只保留最少必要的显式接口。
- [渐进重构会暂时保留部分重复结构] → 接受过渡期冗余，以降低回归风险并保持每一步都可独立验证。

## Migration Plan

1. 创建新的壳层与共享模块，不立即删除旧页面结构。
2. 将首页、归档页和关于页迁移到统一壳层与通用内容布局。
3. 将标签页纳入统一壳层，消除主站与标签页体验分叉。
4. 将 `SideNav`、归档页和标签页切换到共享内容查询模块。
5. 将搜索、播放器和视频组件切换到作用域初始化模式。
6. 在所有页面完成迁移后，删除旧的重复布局与路径拼接逻辑。

回滚策略：若任一阶段出现明显回归，可仅回退当前阶段引入的新布局或共享模块，不影响既有内容文件和页面路由。

## Open Questions

- 是否需要把标签页也统一为带左侧导航的内容布局，还是保留更轻量的独立展示形式。
- 搜索弹窗是否仅作为全局模态存在，还是未来允许在特定页面内嵌搜索区域。
- 播放器是否需要长期支持页面内多个实例；如果需要，后续实现要以多实例为默认前提。
